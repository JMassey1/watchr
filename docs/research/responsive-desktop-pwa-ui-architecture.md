# Responsive Desktop And PWA UI Architecture

## Direct Conclusion

Watch3r should not track a `mobile` or `desktop` device classification in React state and should not create separate mobile routes for the same Watchlist task. Keep one canonical URL and one TanStack Router route tree per task, then make the shared UI responsive to the space and capabilities actually available: viewport size for application chrome, container size for reusable content, and pointer/hover or user-preference media features where those capabilities matter. Media Queries deliberately expose output-device and user-agent features rather than an author-defined device taxonomy; the specification specifically says legacy categories such as `handheld` are inadequate and deprecated in favor of appropriate media features. [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#media-types) [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#media-features)

Use conditional React components only when the UI has a materially different semantic structure or interaction model that cannot be expressed safely by CSS, such as an accessible desktop data table versus a mobile card/list representation, or a browser capability flow such as an install prompt. React supports conditional JSX, but separate trees duplicate behavior, state, and accessibility obligations, so they should share data, actions, labels, and tests rather than become independent "mobile screens." [React: Conditional Rendering](https://react.dev/learn/conditional-rendering)

Treat PWA installation as a **display context**, not a device type. `display-mode` distinguishes browser, standalone, minimal UI, and fullscreen presentation; it does not identify the physical device or establish a desktop/mobile layout. An installed desktop PWA can be resized extremely small, while a phone can be landscape, tablet-sized, paired with a keyboard, or run split-screen. [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#display-modes) [web.dev: App design](https://web.dev/learn/pwa/app-design/)

### Why Not UA Or Device Detection

UA strings are intended to identify browser software and host OS, not an authoritative device class. Browsers routinely include or imitate other browser tokens, and the same OS/browser family can run on multiple form factors. MDN therefore recommends feature detection and responsive CSS; it specifically calls using UA data to decide mobile/tablet/desktop unreliable, and notes that a desktop layout should support touch because desktop devices may have touchscreens. [MDN: Browser detection using the user agent string](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Browser_detection_using_the_user_agent) [MDN: Mobile device detection](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Browser_detection_using_the_user_agent#mobile_device_detection)

Do not replace UA parsing with a `window.innerWidth < ...` value stored as `isMobile` application state. That still loses the actual reason for a choice, reacts poorly to a resizable PWA window, zoom, split view, and container constraints, and makes CSS and JavaScript disagree at boundaries. CSS should own presentational adaptation. If JavaScript genuinely needs an external browser value, subscribe to the underlying browser API rather than copying it once into ad hoc state; React documents `useSyncExternalStore` for external mutable browser APIs. [React: `useSyncExternalStore`](https://react.dev/reference/react/useSyncExternalStore#subscribing-to-a-browser-api)

## Recommended Watch3r Architecture

1. **Route by task, not form factor.** Retain the existing authenticated nested routes and canonical Watchlist deep links. A route selects the user's task and data requirements; it must not select desktop versus mobile rendering. TanStack Router's automatic/file-based splitting can load route components on demand, which addresses bundle size without making a device-specific route tree. [Repository: `apps/web/src/routes`](../../apps/web/src/routes) [TanStack Router: Code Splitting](https://tanstack.com/router/latest/docs/framework/react/guide/code-splitting)
2. **Make the root shell the adaptive boundary.** Evolve `__root.tsx` into semantic shell landmarks: a header containing labeled navigation and one scrolling `main` outlet. Introduce responsive app chrome there, such as a compact top bar and, only if product navigation warrants it, a bottom navigation on constrained windows. Each page should have one top-level main landmark. [Repository: `apps/web/src/routes/__root.tsx`](../../apps/web/src/routes/__root.tsx) [WAI-ARIA APG: Main Landmark](https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/examples/main.html)
3. **Use CSS as the layout engine.** Start with the narrow/base layout, then apply Tailwind breakpoint variants for whole-window changes. Tailwind's unprefixed classes apply at all widths and its breakpoint variants are minimum-width media queries, so `sm:` is not a synonym for "mobile." [Tailwind: Responsive Design](https://tailwindcss.com/docs/responsive-design#working-mobile-first)
4. **Use container queries for reusable Watch3r components.** A Watchlist card, title display, member stack, or action toolbar should adapt to its own parent width if it might appear in a sidebar, grid column, modal, or narrow desktop PWA window. Tailwind supports `@container` and `@...` variants; use them where the component's available inline size, rather than the window, determines its layout. [Tailwind: Container Queries](https://tailwindcss.com/docs/responsive-design#container-queries) [CSS Containment Level 3](https://www.w3.org/TR/css-contain-3/#container-queries)
5. **Keep a small capability layer, not a device store.** Model named facts such as `isStandaloneDisplayMode`, `canPromptForInstall`, `isOnline`, or a particular feature's availability only when behavior needs JavaScript. CSS owns visual `display-mode` differences. `matchMedia('(display-mode: standalone)')` can observe a presentation change when JavaScript must log or change behavior. [web.dev: Detection](https://web.dev/learn/pwa/detection/#detecting-display-mode)
6. **Branch components only at semantic seams.** For a feature that needs distinct desktop and constrained-width structures, export a route-level feature component that owns its query/actions and delegates to two presentational representations. Do not maintain a second route, duplicate loaders, or duplicate domain mutation logic. For CSS-only variations, do not render both interactive copies and hide one: duplicate controls can create duplicate tab stops, names, and landmarks.

### Server Rendering And Hydration

The current Vite entry is client rendered, so browser-only layout facts do not currently create an SSR hydration mismatch. [Repository: `apps/web/src/main.tsx`](../../apps/web/src/main.tsx) If Watch3r later adopts server rendering, neither the server nor the initial HTML can know the client viewport, `matchMedia` result, safe-area value, or installed-PWA display mode. Preserve a deterministic initial tree, let CSS adapt it, and defer JavaScript-only display-mode/capability branches until after hydration. For a browser external store, React requires `getServerSnapshot` to return the same initial value during server rendering and hydration; otherwise server rendering is unsupported for that hook. [React: `useSyncExternalStore` server rendering](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering)

## PWA Windows, Safe Areas, And Keyboards

- Configure a normal PWA launch presentation, normally manifest `display: "standalone"`, but do not make standalone the source of layout breakpoints. `standalone` removes standard browser navigation UI while desktop PWA windows remain independently resizable and can have multiple instances. [web.dev: App design](https://web.dev/learn/pwa/app-design/#standalone-experience) [web.dev: App design](https://web.dev/learn/pwa/app-design/#the-window)
- Use `@media (display-mode: browser)` for browser-only install promotion and `@media (display-mode: standalone)` for small chrome adjustments when needed. Do not use installed state to hide essential navigation, because installed presentation varies and display modes have fallback chains. [web.dev: App design](https://web.dev/learn/pwa/app-design/#display-modes) [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#display-modes)
- Add `viewport-fit=cover` only when Watch3r intentionally paints into device cutout regions. Then apply `env(safe-area-inset-top/right/bottom/left)` padding to the root shell's fixed/sticky app bar, bottom navigation, sheets, and dialogs, keeping essential content and targets outside the unsafe area. [web.dev: App design](https://web.dev/learn/pwa/app-design/#safe-areas)
- Treat keyboard appearance and a small desktop PWA window as constrained viewport cases, not as mobile. Avoid fixed heights for content areas where a keyboard can obscure fields; preserve a scrollable focused field and test the existing `h-svh` shell at narrow width and short height. CSS media queries include both width and height features, and installed desktop apps may be as small as 200 by 100 CSS pixels. [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#height) [web.dev: App design](https://web.dev/learn/pwa/app-design/#optimizing-design-for-desktop)
- Provide a useful route-specific document title. In a standalone desktop PWA, `<title>` contributes to window/task switching presentation. [web.dev: App design](https://web.dev/learn/pwa/app-design/#optimizing-design-for-desktop)

## Tailwind's Role And Limits

Tailwind is an appropriate implementation tool for Watch3r's responsive visual system: mobile-first spacing, grid/flex changes, typography, visibility of decorative content, state styles, breakpoint ranges, and container-query variants. Its responsive utilities compile to media/container queries, which lets the browser update layout as the window or container changes. [Tailwind: Responsive Design](https://tailwindcss.com/docs/responsive-design) [Tailwind: Container Queries](https://tailwindcss.com/docs/responsive-design#container-queries)

Tailwind is not an architecture for classifying devices, choosing routes, managing React state, changing semantic HTML, coordinating focus, determining PWA installation, or replacing a manifest/service worker. Use a small global CSS layer alongside Tailwind for platform primitives such as `env(safe-area-inset-*)`, `@media (display-mode: ...)`, and any named reusable shell tokens; use React only for behavior and genuinely different semantic structures. Tailwind explicitly supports custom CSS when a utility is not the appropriate expression. [Tailwind: Adding Custom Styles](https://tailwindcss.com/docs/adding-custom-styles)

## Accessibility And Testing Checks

- Maintain one keyboard-operable way to reach each destination and Watchlist action in every responsive state. Do not make required controls hover-only; `hover` and `pointer` describe capabilities, not user intent or accessibility needs. [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#mf-interaction)
- Use semantic `header`, `nav`, and `main` landmarks in the app shell. The main landmark identifies primary page content and should be top-level; each page normally has one. [WAI-ARIA APG: Main Landmark](https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/examples/main.html)
- Check focus order after every breakpoint/layout transformation. CSS reordering can make visual and keyboard order diverge; React representation swaps must move focus deliberately rather than leave it on an unmounted control.
- Make navigation, icon controls, and dense Watchlist actions at least 24 by 24 CSS pixels or provide the WCAG spacing alternative. This benefits touch, mouse, pen, and users with reduced fine motor precision, not only phone users. [WAI: Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Test required UI at: a narrow phone portrait width; phone landscape/short height with a software keyboard; tablet split view; ordinary desktop; a narrow standalone desktop PWA window; standalone and browser display modes; touch plus mouse/keyboard; 200% zoom; light/dark, forced-colors, and reduced-motion preferences. The relevant CSS features include viewport dimensions, interaction features, and user preferences. [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#mf-viewport-characteristics) [CSS Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#mf-user-preferences)
- For conditional representations, test the same user task in both structures, exactly one active representation in the accessibility tree, focus preservation across a resize, and no duplicate announced content. For routes, test direct deep links and browser/PWA navigation separately from responsive layout tests.

## Incremental Plan

1. Define a small set of layout decisions from Watch3r content, not device names: constrained/regular/wide shell space and compact/expanded component space. Keep Tailwind's defaults initially; introduce custom breakpoints only after a layout has a demonstrated content-fit threshold. [Tailwind: Customizing Breakpoints](https://tailwindcss.com/docs/responsive-design#using-custom-breakpoints)
2. Refactor the root shell and header first: semantic landmarks, wrapping/overflow behavior, safe-area-aware shell tokens, and a `main` route outlet. Verify its behavior at short/narrow windows before changing individual pages. [Repository: `apps/web/src/routes/__root.tsx`](../../apps/web/src/routes/__root.tsx) [Repository: `apps/web/src/components/header.tsx`](../../apps/web/src/components/header.tsx)
3. Convert repeated Watchlist/title components to base narrow layouts with Tailwind viewport variants. Add a container query only where the same component is used in materially different parent widths. [Tailwind: Responsive Design](https://tailwindcss.com/docs/responsive-design) [Tailwind: Container Queries](https://tailwindcss.com/docs/responsive-design#container-queries)
4. Add display-mode styling to the shell for browser-only installation affordances and standalone spacing/chrome differences. Keep the `display-mode` decision in CSS unless a JavaScript capability flow needs it. [web.dev: App design](https://web.dev/learn/pwa/app-design/#media-queries)
5. Identify any feature where CSS cannot preserve usable semantics at constrained width. Introduce a local alternate React representation only for that feature, sharing its query and mutations and retaining the same canonical route. [React: Conditional Rendering](https://react.dev/learn/conditional-rendering)
6. Add the accessibility and visual regression matrix above to CI or release checks, including browser and installed-PWA contexts. Reassess actual usage before adding a mobile-only information architecture or any separate routes.
